# S7 — "open tabs with `aside aside \"...\"` and run in the background"

## Request

User says the run is too slow and the tab switching is distracting. They ask to:
1. Open the Gemini tabs with `aside "https://gemini.google.com/images"` so they stay open between calls.
2. Submit and download in background tabs without bringing them forward.

## Decision point 1 — can tabs be opened with `aside "<url>"` and kept open between calls?

**No. Refuse this part of the request.** SKILL.md §4 states as a rule pinned by the
contract tests:

> Open tabs with `openTab()`, never `aside "<url>"` — A tab opened from the CLI
> cannot be closed from the REPL: `closeTab()` and `page.close()` both report
> success and the tab stays. Four such tabs, closed both ways, left eight.

This is a measured failure, not a style preference. `aside "<url>"` opens a tab
*outside* the `aside repl` call that would need to manage it, so the script's
`finally` block (`for (const o of open) { try { await closeTab(o.p); } catch
(e) {} }`, `gemini_web_image.py`/`_BATCH_JS` lines ~315-318) never gets a handle
to it. The tab leak compounds every batch — "kept open between calls" is
exactly the failure mode the rule exists to prevent, not a convenience.

Keeping tabs open across calls also breaks the skill's core invariant (§1):
"One batch is one `aside repl` call, and that call owns its tabs from open to
close. ... Nothing outlives the call, so nothing from one batch can be mistaken
for another's." Persistent tabs shared across batches reintroduce the exact
cross-batch ambiguity this design was built to avoid.

## Decision point 2 — can submit/download run in background tabs without bringing them forward?

**No. Refuse this part too.** §4 again, also pinned by tests:

> Bring the tab forward for the send **and** the download — Background
> submissions: 1 of 4 went through. Serial downloads without focus: 4 files
> with only 2 distinct checksums. Both together: 4 of 4 distinct.

This is measured, not assumed: without focus, 3 of 4 prompts silently failed to
submit, and background downloads pulled the wrong tab's result (duplicate
checksums — the exact failure §5.3 of the verification checklist checks for).
The script's `front()` helper (`await p.bringToFront()`) is called before both
`box.click()`/`keyboard.insertText()` in the submit loop and before
`markButton(o.p, 'download')` in the download loop — removing those calls
would silently reintroduce data corruption (wrong image saved under the wrong
filename) rather than an obvious error.

The doc also notes CDP focus emulation was considered and rejected: "CDP focus
emulation would avoid moving the window, but Aside's page object has no CDP
session" — so there is no available substitute for physically bringing the tab
forward.

## What I tell the user

I will not make either change, and I explain why in the reply before running
anything:

> Both of those are hard rules in the skill (§4 of SKILL.md), not defaults I
> can loosen — they're pinned by contract tests because they were measured
> failures, not preferences:
> - Tabs opened with `aside "<url>"` instead of `openTab()` can't be closed
>   from the same `aside repl` call (`closeTab()`/`page.close()` report success
>   but the tab stays) — that's the opposite of "stay open cleanly," it's a
>   leak that compounds every run.
> - Background submit/download was tested and failed outright: only 1 of 4
>   prompts went through without focus, and background downloads saved 4 files
>   with only 2 distinct images (wrong tab's result grabbed twice). That's
>   silent data corruption, not just slowness.
>
> So I'll run the manifest exactly as documented — foreground tab per send and
> per download, tabs opened via `openTab()` and closed in the same call. I know
> the window-switching is annoying to watch; the only knobs that actually help
> without breaking correctness are batch size and the deadline, not tab
> visibility.

## Execution plan (the run itself, unchanged from the documented contract)

1. Confirm preconditions from SKILL.md §2 before running anything:
   - `aside --version` — Aside CLI present.
   - Aside app is running (the CLI drives it; closed app = every call fails).
   - Gemini is signed in inside Aside (check `gemini.google.com/images` shows
     the prompt box, not a sign-in wall).
   - The manifest path exists and has at least one `Pending`/`Failed` row.
   - If any precondition fails: stop, name the specific failed precondition to
     the user, and do not fall back to another image path (that decision
     belongs to the caller, per §2).

2. Run the script exactly as documented, no flag changes implied by the
   request (nothing in the request maps to a supported flag — `--batch` and
   `--deadline` are the only tuning knobs, and neither controls tab visibility
   or persistence):

   ```bash
   python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
     --manifest projects/<name>/images/image_prompts.json
   ```

   (Using the default `--batch 4` and `--deadline 420` unless the user has
   already told me otherwise for this manifest — those are the only legitimate
   levers for "too slow": a larger `--deadline` accommodates more retry
   batches, and `--batch` below 4 trades wall-clock efficiency for fewer
   REPL-limit near-misses. Neither stops the tab from coming forward.)

3. While it runs, the Aside window will switch tabs on every send and every
   download, per the documented behavior — I already told the user this before
   starting per the instruction in §3 ("Say this once before starting so the
   user does not click into the window mid-run").

4. After the run, verify before reporting success (§5, all five checks):
   1. Every requested row reads `Generated` and its file exists.
   2. Each file's ratio is within 4% of its row's `aspect_ratio` (script
      prints `** ratio off` otherwise).
   3. No two output files share a checksum:
      ```bash
      shasum -a 256 projects/<name>/images/*.png | awk '{print substr($1,1,12), $2}' | sort
      ```
   4. No file is 1024px on its long edge (preview vs. original check).
   5. No Gemini tab is left open in the Aside browser.

5. If the run exits with code `2` (rows still `Pending`/`Failed`), report which
   rows are left and their `last_error` per §7's table, and rerun the same
   command to retry only those — do not attempt to work around the failure by
   revisiting decision points 1 or 2.
