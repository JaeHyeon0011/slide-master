# Plan: all 4 rows Failed with "aside repl returned no result (... isn't running ...)", Aside app visibly open

## Context

SKILL.md §7 maps this exact `last_error` text to a two-branch action:

> `aside repl returned no result (... isn't running ...)` | Either the Aside
> app is closed or a call ran past 120s. Open the app and rerun; if it recurs
> with the app open, lower `--batch`

The script's own `find_aside()` / startup path only prints the "Aside CLI not
found" message when the `aside` binary itself is missing from PATH and the
known install locations (`gemini_web_image.py` lines 524-529); that is a
different failure (exit 1, manifest untouched) and is not what happened here —
we got four `Failed` rows with `last_error` set, which only happens inside
`run_batch()` when `parse_result(out)` returned `None` for a completed `aside
repl` invocation (lines 421-431). Per the code comment at lines 67-70 and 423-425,
that specific message is produced when the REPL call returns no
`ASIDE_RESULT ...` line, which happens either because the Aside app was not
running when the CLI tried to drive it, or because the JS ran past the 120s
hard limit and the connection dropped.

Since the task states the Aside app is "visibly open," the "app is closed"
half of the disjunction is already contradicted by what I can see — but I
cannot fully trust a visual impression over the tool's own diagnosis without
checking, and the message explicitly names a second cause (a call that ran
past 120s) that looks identical from the manifest's point of view. So the plan
does not skip straight to "lower --batch"; it first confirms the app is
genuinely reachable by the CLI (not just visually open — it could be open but
unresponsive, mid-relaunch, or running a stale/crashed helper process), then
follows the branch the evidence actually supports.

## Step-by-step execution plan

1. **Do not immediately rerun the full manifest.** Rerunning blind on a
   4-for-4 failure risks repeating the same failure mode (and, if the real
   cause is a >120s call, wasting another full deadline budget) without
   learning anything. Diagnose first.

2. **Confirm the Aside CLI itself is responsive**, independent of whether the
   app window is visible:
   ```bash
   aside --version
   ```
   - Branch A — command errors or hangs: the CLI cannot reach the app process
     even though a window is on screen (e.g., app is relaunching, frozen, or a
     second stale instance is running). Tell the user: "The Aside app is open
     but the CLI can't reach it (`aside --version` failed/hung). Please quit
     Aside fully and reopen it, then let me know." Wait for confirmation
     before proceeding to step 4.
   - Branch B — command returns a version promptly: the CLI can talk to the
     app, so the "app is closed" explanation is ruled out and the likely
     cause is a call that ran past the 120s REPL limit (SKILL.md §7, second
     half of that row; also consistent with §4's "Keep each call inside 105s"
     rule and the `REPL_LIMIT = 120` / `BUDGET = 105` constants at lines
     70-71). Proceed to step 3.

3. **Do a minimal live check that Gemini itself is reachable in Aside**,
   since a >120s call is often caused by the page never reaching a usable
   state (sign-in wall, challenge page, slow load) rather than pure timing.
   Ask the user to glance at the Aside window (or, if permitted, drive it
   myself) and confirm `gemini.google.com/images` shows a signed-in prompt
   box, per the Preconditions table in SKILL.md §2. This is a real decision
   point:
   - If the page shows Google's `google.com/sorry/...` challenge or an
     `accounts.google.com` sign-in wall: stop here. This is outside this
     skill's authority to clear (§4: "Stop on `google.com/sorry/` or a
     sign-in page ... Only a person can clear it in the Aside browser"). Tell
     the user exactly that, and ask them to clear it by hand in the Aside
     browser before I rerun anything.
   - If the page is a normal signed-in Gemini prompt box: proceed to step 4.

4. **Rerun the same command exactly as before, unmodified**, since §7's
   first instruction for this error is "Open the app and rerun" and the app
   was already open — nothing to change yet:
   ```bash
   python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
     --manifest <path-to-manifest>/image_prompts.json
   ```
   Before running, tell the user: "Rerunning the same command — the Aside
   window will switch tabs while it submits and downloads, so please don't
   click into it mid-run" (per SKILL.md §3's standing warning). This is a
   regular action (no side effects requiring explicit permission beyond
   normal script execution) since it only touches the project's own
   manifest/output files, consistent with `deliver-path-not-file-card.md`
   memory guidance — I report the resulting path, not a file card.

5. **Read the result and branch on what happened:**
   - **All 4 rows now read `Generated`, exit code 0**: success. Run the
     Verify-before-reporting-success checklist in SKILL.md §5 (ratio within
     4% per row, no duplicate checksums via `shasum -a 256 .../images/*.png |
     awk '{print substr($1,1,12), $2}' | sort`, no file with long edge
     ==1024px indicating a preview was saved instead of the original, no
     Gemini tab left open in Aside). Report success with the manifest path.
   - **Some rows `Generated`, some still `Failed` with a *different*
     `last_error`** (exit code 2): do not treat this the same as the original
     failure. Look up the new `last_error` text against the SKILL.md §7 table
     and follow that row's specific action (e.g., a `no_box` /
     `prompt box never appeared` error sends me back to check the URL for a
     challenge/sign-in page; a `download` failure means rerunning once more
     is the documented action; etc.). Do not invent handling not in that
     table.
   - **All 4 rows fail again with the same `"aside repl returned no
     result (... isn't running ...)"` message**: this is the "recurs with the
     app open" case SKILL.md §7 explicitly anticipates. Its documented
     action is "lower `--batch`". Rerun with a reduced batch size, e.g.:
     ```bash
     python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
       --manifest <path-to-manifest>/image_prompts.json \
       --batch 1
     ```
     (Starting at `--batch 1` rather than an intermediate value like 2,
     because with only 4 rows total there is no meaningful cost difference,
     and `--batch 1` isolates whether the problem is batch-size/timing
     related at all — if even a single-row batch times out, that points away
     from "too many tabs" and toward a systemic problem, which I would then
     report to the user rather than continuing to retry blindly.)
   - **Even `--batch 1` reproduces the same error**: stop and report to the
     user rather than continuing to retry indefinitely. Tell them: the CLI
     accepts a version check and the app appears open, but every `aside repl`
     call is returning no result even for a single row — this points at
     something SKILL.md doesn't have a documented fix for (e.g., a broken
     Aside helper process, network issue, or an Aside version regression).
     Suggest they fully quit and relaunch the Aside app once more, or check
     `aside --version` output for a version mismatch, and offer to retry
     after they've done so. Do not fall back to another image-generation path
     from inside this skill — SKILL.md §2 explicitly reserves that decision
     for the caller ("Stop and name the failed precondition. Do not fall back
     to another image path from inside this skill").

6. **Never re-submit rows that already read `Generated`.** At every rerun in
   this plan, `RETRYABLE = {"Pending", "Failed"}` (script lines 55-57) means
   the script itself only re-sends `Pending`/`Failed` rows and treats the run
   as idempotent — I do not need to (and must not) manually edit the
   manifest to force a resend of a `Generated` row unless the user
   specifically wants that row redone, in which case SKILL.md §3 says to set
   its status back to `Failed` first, and I would confirm that with the user
   before editing the manifest by hand.

## What I tell the user, in order

1. Before step 2: nothing yet — step 2 is a silent diagnostic (`aside
   --version`), not a side-effecting action.
2. If Branch A (CLI unresponsive): ask them to quit and reopen Aside, and
   wait for their go-ahead.
3. If step 3 finds a challenge/sign-in wall: ask them to clear it by hand in
   the Aside browser, and wait for confirmation before rerunning.
4. Immediately before step 4's rerun: warn that the Aside window will switch
   tabs during the run and ask them not to click into it.
5. After the rerun resolves (success, partial, or the same failure recurring
   at `--batch 1`): report the outcome plainly — what saved, what's still
   `Failed` and why (quoting the `last_error`), and the manifest's path,
   without wrapping the result in a file card.
