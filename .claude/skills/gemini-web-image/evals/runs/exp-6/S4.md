# Execution plan — 3-row manifest, row 2 already 16:9-prefixed and matching, row 3 already 16:9-prefixed but aspect_ratio is 1:1

## 0. What's special about this manifest

- Row 2: `prompt` already starts with `Generate a 16:9 image (aspect ratio exactly 16:9).`, and `aspect_ratio` is `16:9`. Line and field agree.
- Row 3: `prompt` starts with the **same** `Generate a 16:9 image (aspect ratio exactly 16:9).` line, but `aspect_ratio` is `1:1`. Line and field disagree.

`with_ratio()` in `scripts/gemini_web_image.py` (lines 111–127) is idempotent only when the existing line's ratio matches the row's `aspect_ratio`:
- If the prompt already opens with the exact line for the row's own ratio, it is returned unchanged (row 2's case — no duplicate line).
- If the prompt opens with a ratio line naming a **different** ratio than the row's `aspect_ratio` (row 3's case), the function logs `** prompt opens with a 16:9 ratio line but the row asks for 1:1; sending the row's ratio in front of it` and **prepends** the correct line anyway — it does not strip the stale one. The prompt actually sent to Gemini would become two contradictory sentences back to back: `Generate a 1:1 image (aspect ratio exactly 1:1).\n\nGenerate a 16:9 image (aspect ratio exactly 16:9).\n\n<rest of prompt>`.

SKILL.md §4 calls this out explicitly: "a line naming a different ratio is reported" — it is treated as a manifest authoring error, not something the script should silently paper over by sending contradictory instructions to the model.

## 1. Before the run

1. Confirm preconditions from SKILL.md §2:
   - `aside --version` succeeds (Aside CLI installed).
   - The Aside app is running.
   - `gemini.google.com/images` is signed in inside Aside (check the prompt box renders).
   - The manifest file is valid JSON with at least one `Pending`/`Failed` row.
   - If any of these fail, stop and name the failed precondition to the user — do not fall back to another image path from inside this skill.

2. Read the manifest and inspect every row's `prompt` against its `aspect_ratio` **before** invoking the script, specifically checking for a leading `Generate a <ar> image (aspect ratio exactly <ar>).` line that names a ratio other than the row's own `aspect_ratio`. This is exactly row 3.

3. **Decision point — row 3's stale ratio line.**
   - Branch A (let the script handle it silently): do nothing, let `with_ratio()` prepend the correct line on top of the stale one at runtime. Rejected — this sends Gemini a prompt with two contradictory aspect-ratio sentences (`1:1` then `16:9`), which is the exact failure mode the code comment at line 121 calls out ("the two sentences would contradict each other on the page"). Relying on the model to prefer the first line over the second is not something the skill or script guarantees.
   - Branch B (fix the manifest before running): edit row 3's `prompt` field to remove the stale leading `Generate a 16:9 image (aspect ratio exactly 16:9).` line (and the blank line after it) so the prompt starts directly with its actual content. **Take this branch.** After the edit, `with_ratio()` will cleanly prepend `Generate a 1:1 image (aspect ratio exactly 1:1).` with nothing left to contradict it, and row 2 needs no edit since its line already matches.

4. Save the corrected manifest back to `image_prompts.json` before running anything.

5. Tell the user, before starting: "Row 3's prompt carried a stale 16:9 ratio line that didn't match its 1:1 `aspect_ratio` — I removed the stale line before sending so the two rows don't get contradictory prompts. The Aside window will switch tabs while this runs (it opens a tab per row, brings each one forward to type and to download); please don't click into the Aside window until it finishes."

## 3. During the run

1. Watch the timestamped log lines. Expect, per row: a `submit` timing, a `ready at` timing, a `download` timing, then `saved <filename> <w>x<h> ratio <actual> vs <target>`.
2. Decision point — any `**` line in the log:
   - `** prompt opens with a <x> ratio line but the row asks for <y>...` — should **not** appear for either row now, since row 3 was fixed pre-run and row 2 already matched. If it appears anyway (e.g., the manifest edit didn't take), stop, re-check the manifest on disk, and rerun rather than trusting the in-flight contradictory prompt.
   - `** ratio off, review this row` — the saved file's actual ratio is more than 4% off its row's `aspect_ratio`. That row needs a resubmit (set its `status` back to `Failed` and rerun), not a footnote.
   - `** <n> row(s) saved at the 1024px preview size instead of the original` — the inline preview was saved instead of the original download; treat as not actually done for those rows.
3. Decision point — `stopping: the page went to ...` (Google's `sorry/` challenge or a sign-in wall): stop reporting progress, tell the user this needs to be cleared by hand in the Aside browser, and that finished rows are kept. Do not retry automatically.
4. Decision point — a row logs `gemini-web: aside repl returned no result (... isn't running ...)`: either the Aside app closed or a call ran past 120s. Reopen the app and let the script's own retry pass resend it; if it recurs, lower `--batch` on the next invocation.
5. The script itself retries failed rows once within the same run (its internal retry pass) — no manual intervention needed for a single failure unless it fails that second time too, in which case the row stays `Failed` with `last_error` set.

## 4. After the run — verify before reporting success (SKILL.md §5)

1. Confirm all 3 rows read `Generated` in the manifest and each row's file exists on disk.
2. For each file, confirm its actual pixel ratio is within 4% of its row's `aspect_ratio` (row 2 and row 3 should now come back close to 16:9 and 1:1 respectively, matching the measured values in §5.1 of SKILL.md: 16:9 → ~2752×1536, 1:1 → ~2048×2048). Any `** ratio off` line means that row needs a resubmit, not a pass.


5. Confirm no Gemini tab is left open in the Aside browser (the script's `finally` block closes every tab it opened; spot-check visually if in doubt).
6. Check the script's exit code: `0` means every row finished; `2` means rows are still `Pending`/`Failed` and the same command should be rerun to retry only those.
