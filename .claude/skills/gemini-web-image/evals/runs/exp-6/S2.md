# Execution plan — manifest with 2 Generated, 1 Needs-Manual, 4 Failed

Scenario: `image_prompts.json` has 7 rows total — 2 `Generated` (files already on
disk), 1 `Needs-Manual`, 4 `Failed` from an earlier attempt.

## 0. Preconditions (§2)

Check these before running anything; stop and name the failed one instead of
falling back to another image path.

1. `aside --version` — confirms the Aside CLI is installed.
2. Confirm the Aside app is running (the CLI drives it; a closed app fails every
   call).
3. Open `gemini.google.com/images` in the Aside browser and confirm the prompt
   box renders — confirms Gemini is signed in inside Aside's own profile.
4. Confirm the manifest path exists and is valid JSON with at least one
   `Pending` or `Failed` row — here, the 4 `Failed` rows satisfy this.

If any of these fails, stop and tell the user exactly which precondition
failed (e.g. "Aside app is not running — open it and sign in to Gemini, then
tell me to retry"). Do not silently switch to a CLI/API image path.

## 1. Tell the user before starting

State once, before the first batch: "The Aside window will switch tabs while
this runs — sending prompts and downloading images both bring their tab to the
front. Please don't click into the Aside window until this finishes." (§3)

Also note: only the 4 `Failed` rows will be touched. The 2 `Generated` rows are
left alone (already done, files on disk), and the 1 `Needs-Manual` row is never
submitted — it belongs to the user (§3 "Idempotent").

## 2. Run

```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/<name>/images/image_prompts.json
```

No `--batch` or `--deadline` override needed: 4 rows fit in one batch of the
default/max size 4, well inside the default 420s deadline.

## 3. What the script does with these 7 rows (internal, no separate commands)

1. Loads the manifest, filters `manifest["items"]` to `status in {Pending,
   Failed}` → exactly the 4 `Failed` rows. The 2 `Generated` and 1
   `Needs-Manual` rows are excluded by this filter alone.
2. Seeds `seen` (the checksum dedup set) by hashing the on-disk files of the 2
   `Generated` rows, so a rerun can't save a new file that collides with a file
   that already finished.
3. `plan_batches` splits the 4 `Failed` rows into batches of size ≤4 — with 4
   rows and batch size 4, this is a single batch of 4.
4. Runs that batch as one `aside repl` call (`run_batch`):
   - Opens one tab per row via `openTab()` (never `aside "<url>"`).
   - Submits each prompt serially, bringing each tab to front first, typing
     with `keyboard.insertText()`, and requiring a `model-response` element or
     a `/app/<id>` URL before counting the row as sent.
   - Waits for each row's image, bringing the tab to front to download,
     verifying the downloaded file's checksum is not already in `seen`.
   - Writes each row's outcome (`Generated` + cleared `last_error`, or
     `Failed` + `last_error`) back to the manifest immediately as it lands.
   - Closes every tab it opened, in `finally`, regardless of outcome.
5. Any row that failed in this first pass goes into `retry`; when the batch
   queue is empty and `retry` is non-empty, one more batch is built from those
   rows and run the same way (§3 "Failures retry once, in the same run").
6. If a batch hits Google's challenge or a sign-in wall (`CHALLENGE_RE`), the
   run stops immediately and keeps whatever already saved — this is a decision
   point handled entirely inside the script, not something I branch on
   manually.

## 4. Decision points and the branch taken

- **Exit code 0 (all 4 saved, 6/7 `Generated` total after this run — the
  `Needs-Manual` row never turns `Generated`)** → proceed to verification
  (§5) and report success.
- **Exit code 2 (some rows still `Pending`/`Failed` after the retry pass)** →
  do not treat this as a hard failure. Read each remaining row's
  `last_error` and cross-reference §7's table:
  - `aside repl returned no result (... isn't running ...)` → check the Aside
    app is open; rerun the same command. If it recurs with the app open,
    rerun with a lower `--batch` (e.g. `--batch 2`).
  - `prompt box never appeared at <url>` → read the URL. If it's
    `google.com/sorry/...` or `accounts.google.com`, this is already covered
    by the "blocked" stop below — clear it by hand in the Aside browser, then
    rerun. Otherwise the page structure changed; investigate with `aside repl`
    + `snapshot()` before editing selectors (a script/skill change, out of
    scope for a plain rerun).
  - `prompt typed but the answer never started` → the built-in retry pass
    already resent it once; if it's still failing, check the page by hand for
    a dialog covering the prompt box.
  - `no image inside the batch budget; page ends with: ...` → read the quoted
    tail. If it reads as a refusal, reword that row's prompt before
    resubmitting (edit the manifest's `prompt` field, set `status` back to
    `Failed`, rerun).
  - `the batch's 105s budget ran out ...` → nothing to change; rerunning the
    same command retries it.
  - `image shown but the download failed` → rerun; if every row fails this
    way, the download control likely changed on the page (script issue, out
    of scope for a plain rerun).
  - `identical to <file> — tab isolation broke` → resubmit (rerun); if this
    recurs, the focus rule in §4 of the skill is not holding (script issue).
  - In all of the above, the default action is: **rerun the exact same
    command** (`gemini_web_image.py --manifest ...`) — it only resubmits rows
    still `Pending`/`Failed`, so this is safe and idempotent. Only escalate to
    editing a prompt, lowering `--batch`, or investigating selectors when the
    `last_error` calls for that specific action.
- **Run stopped early on `google.com/sorry/` or a sign-in page (`blocked`
  set)** → stop immediately, do not retry automatically. Tell the user: "The
  run hit Google's unusual-traffic check / a sign-in wall at <url>. Please
  clear it by hand in the Aside browser, then tell me to rerun." Finished rows
  from this run are already saved and kept.
- **Deadline reached before all batches ran** (not expected here — 4 rows is
  one batch, well under 420s) → the script logs how many rows are left unsent
  and stops; rerun the same command to pick them up.

## 5. Verify before reporting success (§5)

1. Confirm all 4 previously-`Failed` rows now read `Generated` in the manifest
   and their files exist on disk (the 2 already-`Generated` rows and the 1
   `Needs-Manual` row are unaffected and already known-good).
2. For each newly-saved file, confirm the script did not print a `** ratio
   off` line; if it did, that row needs a resubmit (set `status` back to
   `Failed`, rerun), not a footnote.
3. Confirm no two output files share a checksum across the full set (all 6
   `Generated` files, old and new):
   ```bash
   shasum -a 256 projects/<name>/images/*.png | awk '{print substr($1,1,12), $2}' | sort
   ```
4. Confirm the script printed no `**` line about a file saved at the 1024px
   preview edge; an absent line is the pass.
5. Confirm no Gemini tab is left open in the Aside browser (spot-check the
   window, since every tab this run opened should have been closed in
   `finally`).

## 6. Report to the user

State the final counts: e.g. "4/4 previously-failed rows generated this run;
manifest now has 6/7 `Generated` and 1 `Needs-Manual` (waiting on your own
file). All checksums distinct, all ratios within tolerance, no preview-size
files, no tabs left open." If any row is still `Failed` after the built-in
retry, name it and its `last_error`, and state the specific next action from
§4 above rather than declaring the run complete.
