# Execution plan — fill projects/demo/images/image_prompts.json (6 Pending rows)

## 0. Preconditions (§2)

Before running anything, confirm all four:

1. Aside CLI installed — check `aside --version`.
2. Aside app running — the scenario states the Aside app is running, so this is satisfied; still, do not proceed silently if a later step reports the app unreachable.
3. Gemini signed in inside Aside — the scenario states the Aside browser is signed in to Gemini, so this is satisfied.
4. Manifest is valid `image_prompts.json` with at least one `Pending`/`Failed` row — the scenario states 6 rows, all `Pending`, so this is satisfied.

Decision point: if any precondition were false, stop and name the failed precondition to the user; do not fall back to another image path (e.g. a CLI/API backend) from inside this skill — that decision belongs to the caller, not this run. Since all four preconditions hold here, proceed.

## 1. Tell the user before starting

Say, once, before running the script:

> "This will run through the Aside browser and will switch tabs in front of you while it submits prompts and downloads images — please don't click into the Aside window until it finishes."

This is required by §3 ("Say this once before starting so the user does not click into the window mid-run").

## 2. Run the script

Single command, no flags beyond `--manifest` needed since defaults are appropriate:

```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/demo/images/image_prompts.json
```

Rationale for defaults:
- `--output` omitted → images write to `projects/demo/images/` (the manifest's own folder), which is correct here.
- `--batch` omitted → defaults to 4 (the max). With 6 Pending rows this produces two batches: batch 1 = 4 rows, batch 2 = 2 rows (per `plan_batches`, which packs greedily up to `size` or the 30,000-char argument limit, whichever binds first).
- `--deadline` omitted → defaults to 420s. Per §5.1 timing, 10 rows run as 4+4+2 in ~3.5–4 min; 6 rows (4+2) will be comfortably under the 420s default, so no need to raise it.

I do not pass `--batch` lower than 4 — nothing in the scenario suggests the default 105s-per-batch budget is at risk, and a smaller batch only adds more serial per-batch overhead.

## 3. What the script does per batch (internal mechanics, not separately invoked)

For each batch (first the 4-row batch, then the 2-row batch, plus any retry batches):

1. Build the batch JS job list via `with_ratio()`, which prepends `Generate a <ar> image (aspect ratio exactly <ar>).` to each row's prompt — once, and only if that exact line isn't already present. For this manifest's 6 rows that means:
   - 4 rows get `Generate a 16:9 image (aspect ratio exactly 16:9).` prefixed.
   - 1 row gets `Generate a 4:3 image (aspect ratio exactly 4:3).` prefixed.
   - 1 row gets `Generate a 1:1 image (aspect ratio exactly 1:1).` prefixed.
   - Decision point: if any prompt already opened with a *different* ratio line than its row's `aspect_ratio`, the script logs a `**` warning and sends the row's correct ratio in front anyway (it does not stop the run over this).
2. Run one `aside repl` call per batch (`run_js`), budgeted to 105s of JS-internal work under the REPL's 120s hard limit.
3. Inside that call: open one tab per row via `openTab()` (never `aside "<url>"`), submit prompts serially (each tab brought to front first, prompt typed with `keyboard.insertText()`, send tried via Enter then the send button, confirmed only once a `model-response` element exists or the URL moves to a conversation), with randomized 700–2000ms gaps between sends.
4. Wait for each row's image and download it serially (tab brought to front first again), refusing to start a download with less than 22s left in the batch budget.
5. Close every tab that batch opened, in a `finally`, regardless of outcome.
6. Back in Python (`run_batch`): for each row, read the downloaded file, hash it, and:
   - Decision point — duplicate checksum: if the digest matches an already-seen file (from this run or a prior `Generated` row on disk), mark that row `Failed` with `last_error` "identical to <file> — tab isolation broke; resubmit" and do NOT write the file as that row's output.
   - Decision point — ratio check: compute actual W/H from the PNG/JPEG header vs `aspect_ratio`. If out of the 4% tolerance, still save the file and mark `Generated`, but log a `** ratio off, review this row` line — this is a review flag, not a failure state.
   - Decision point — preview-size check: if `max(width, height) <= 1024`, log it in the `previews` list (still `Generated`, but flagged as the inline preview, not the original).
   - Otherwise mark the row `Generated`, clear `last_error`, and write the manifest back to disk immediately (so an interrupted run keeps completed rows).
7. Decision point — Google challenge/sign-in wall: if any row's probed URL matches `google.com/sorry/` or `accounts.google.com`, the run stops after finishing the current batch's already-decided rows; it does not proceed to further queued batches. This requires a human to clear it in the Aside browser, then rerun. (Not expected here since Gemini is already signed in, but the plan must account for it.)

## 4. Retry pass (within the same run, §3 "Failures retry once")

After the two initial batches (4-row, then 2-row) run, any rows left `Failed` (and not blocked by a challenge/sign-in wall) are collected and resent once, in fresh batches sized the same as before (up to 4 rows per batch). This happens automatically inside `main()` — I do not invoke the script a second time for this; it's one process, one command, one report at the end.

Decision point: if a row fails again on the retry pass, it stays `Failed` with `last_error` set and is left for me to report, not resubmitted a third time within this run.

## 5. After the script exits — verify before reporting success (§5)

Run these checks in order:

1. **Status/file check**: read the manifest back and confirm every one of the 6 target rows reads `status: "Generated"` and its `filename` exists on disk in `projects/demo/images/`.
2. **Ratio check**: for each saved file, confirm width/height is within 4% of its row's `aspect_ratio`. The script already prints a `** ratio off` line per offending row during the run — cross-check the log output rather than re-deriving it, but re-verify if any `**` line appeared. A flagged row needs a resubmit (set `status` back to `Failed` and rerun), not a footnote.
3. **Checksum uniqueness**: run
   ```bash
   shasum -a 256 projects/demo/images/*.png | awk '{print substr($1,1,12), $2}' | sort
   ```
   and confirm no two lines share the same leading hash. (The script already refuses to save a duplicate at write time, so this is a final sanity pass over the full set, not an expectation of finding one.)
4. **Preview-size check**: confirm no output file is 1024px on its long edge. The script's `**` log line during the run names any such row; if that line is absent, this check passes.
5. **Tab-leak check**: confirm no Gemini tab is left open in the Aside browser (the `finally` block closes all tabs it opened; this is a manual visual/API confirmation, not a script output).

Decision point: if step 2 or 4 flags a row, I do not report that row as clean — I either resubmit it (status → `Failed`, rerun the same command so only that row is retried, since the script only takes `Pending`/`Failed` rows) or explicitly call it out to the user as needing manual review, per which the user prefers.

## 6. Reporting to the user

After verification, report:
- How many of the 6 rows are `Generated` vs still `Failed`/`Pending`.
- Per-row: filename, resolution, aspect ratio matched (16:9 ×4, 4:3 ×1, 1:1 ×1) or flagged.
- Any `**` flags surfaced (ratio off, preview-size, duplicate checksum) with the specific filenames.
- If any row is still `Failed` after the retry pass, quote its `last_error` and map it against §7's table (e.g. "prompt box never appeared" → check the URL for a challenge/sign-in wall; "no image inside the batch budget" → likely a refusal, reword the prompt) rather than just repeating the raw error.
- Confirm no tabs were left open in Aside.
- If the exit code was `2` (rows still Pending/Failed), tell the user explicitly that a rerun of the same command will retry only the unfinished rows — I do not invoke the script a third time within this same task without the user's go-ahead, since a `Failed` row after one retry pass may need a prompt reword or a manual look at Aside, not a blind rerun.

## 7. What I do NOT do

- I do not touch any `Needs-Manual` rows (none exist in this manifest, but if they did, they are never submitted).
- I do not fall back to another image backend (CLI/API) myself if this fails — that decision belongs to the caller.
- I do not manually open tabs with `aside "<url>"` or otherwise hand-drive the browser outside the script — the script owns tab lifecycle end-to-end via `openTab()`/`closeTab()`.
- I do not lower `--batch` below 4 or raise `--deadline` beyond 420 preemptively; I only do so if a run actually shows the "aside repl returned no result" / "isn't running" failure pattern from §7, which would indicate a call ran past the REPL's 120s limit.
