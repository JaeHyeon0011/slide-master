## Step 1 — Run the script

```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest <manifest>
```

(`--output`, `--batch`, `--deadline` all left at default: output folder =
manifest's folder, batch size 4, deadline 420s — 4 rows fit one batch under
the default, so there is no reason to override any of them.)

Before the first `aside repl` call, `main()` runs through, in order:

- Reconfigures stdout/stderr to UTF-8 (Windows console mojibake guard — not
  relevant to the branch taken here beyond "it always happens first").
- `find_aside()` — same check as Step 0.1, done again by the script itself.
  - **Branch — not found**: script logs the install message and
    `sys.exit(1)`. The manifest is untouched. I'd relay that exact message to
    the user and stop.
  - **Branch — found**: continue.
- Loads `<manifest>`, sets `out_dir` to the manifest's own folder (no
  `--output` given).
- Builds `pending = items with status in {Pending, Failed}` → **exactly the 4
  `Failed` rows**. The 2 `Generated` rows and the 1 `Needs-Manual` row are
  excluded here by construction — nothing else in the run needs to special-
  case them.
  - **Branch — `pending` empty**: script logs "nothing to do" (naming the
    `Needs-Manual` count too) and returns 0. Not taken here.
  - **Branch — `pending` has rows (4 here)**: continue.
- `plan_batches(pending, size=4)`: builds the Windows-quoted command line for
  the trial batch and only closes a batch early if adding the next row would
  exceed 4 rows or cross the 30,000-char argument limit.
  - **Branch — 4 short/medium prompts stay under 30,000 chars as one
    `aside repl` argument**: all 4 `Failed` rows land in **one batch of 4**.
    This is the expected branch for a normal-length manifest.
  - **Branch — the 4 prompts together would cross 30,000 chars**: `plan_batches`
    splits into two batches (e.g. 3 + 1) instead. I don't know prompt length
    from the scenario, so I note this branch but plan around the expected
    one; if the real manifest's prompts are long, the log line in the next
    step ("N row(s) in M batch(es)") tells me which branch was actually
    taken, and everything below still applies per-batch.
- Logs: `4 row(s) in 1 batch(es) of up to 4; the Aside window can stay
  covered or minimized while it runs` (or `2 batch(es)` if the split branch
  above was taken). **This is the first thing I relay to the user** — it also
  doubles as confirmation the run only picked up the 4 `Failed` rows, not the
  `Generated` or `Needs-Manual` ones.
- Seeds `seen{}` with the SHA-256 of every `Generated` row's file that exists
  on disk — **both of the scenario's 2 pre-existing images go in here**. Any
  new download whose bytes match one of them is rejected later as a
  cross-tab mixup, not accepted as a coincidence.

## Step 2 — The batch call(s)

The run loop pops one `(batch, is_retry)` at a time:

- **Deadline gate, before every pop**: if `time.time() + 120s` would cross
  `run_started + 420s`, the script stops early, logs how many rows are left
  unsent, and tells the caller to re-run for them. On the very first batch of
  a fresh 420s run this is never true, so it isn't taken here unless the
  precondition-check step above already burned most of the budget — it
  won't, since nothing in Step 0 calls `aside`.
- Logs `batch: row0.png, row1.png, row2.png, row3.png` (the four `Failed`
  rows, by their manifest filenames) — **second thing I relay to the user**.
- `run_batch()` fires one `aside repl` call carrying all 4 jobs, each with its
  aspect-ratio line prepended by `with_ratio()` (added only if the row's own
  prompt doesn't already open with the matching ratio sentence; if it opens
  with a *different* ratio, the script logs a `**` warning and still sends
  its own line in front — I would read that warning if it appears, since it
  means the manifest itself may have a stale/wrong `aspect_ratio` value worth
  flagging back to the user separately from this run's outcome).

Inside that one call (per `_BATCH_JS`, mirrored in SKILL.md §4), for each of
the 4 rows in order: open a tab with `openTab()`, wait for the prompt box
`attached` (not visible — the window may be covered/minimized), focus it via
JS, type with `keyboard.insertText()` and verify length, fall back to
`execCommand('insertText')` if that under-shot, send with Enter then the
send-icon button, confirm the answer actually started (`model-response`
element or a `/app/<id>` URL — not just "the click didn't throw"), then a
randomized 0.7–2.0s pause before moving to the next row. Any row whose prompt
box never appears, whose typed length stays under 10 chars, or whose send
never starts, is marked with its own failure `kind` and the loop moves to the
next row — one row's failure does not stop the batch.

Once submission is done for all sent rows, it polls readiness (a download
button inside the last `model-response`) and, for each row as it becomes
ready: activates that row's tab (the one focus-touching step, needed only
because Aside routes a download to the active tab), clicks the download
icon, and reads `download.path()`. A downloaded name already seen earlier in
*this* batch is re-clicked (up to 2 retries) rather than accepted, since a
repeated name means the previous row's file was handed over again.

**Branches on the batch's overall result** (`run_batch`, after the call
returns):

- **(a) No parseable `ASIDE_RESULT`/`ASIDE_ROW` output at all** (e.g. Aside
  app not running or the call ran past 120s with nothing printed): every row
  in the batch is set to `Failed` with
  `last_error = "gemini-web: aside repl returned no result (<reason>)"`, the
  manifest is saved immediately, and the batch reports 0 saved / all 4
  failed. This is the branch that would actually reveal a Step-0.2
  precondition I couldn't confirm myself (Aside app closed, or never signed
  in far enough for the URL to resolve before the call's own 120s cutoff).
  I'd read the reason string and, if it says "isn't running", tell the user
  to open the Aside app and re-run rather than reinstalling anything.
- **(b) Partial output** (call cut off mid-batch, some `ASIDE_ROW` lines
  already printed): rows already reported as saved are kept from
  `artifacts/`; every other row in the batch is treated as `cut_off`. I'd
  relay this as "the call was cut off; N of 4 rows had already saved."
- **(c) Full result, row-by-row**, for each of the 4:
  - Row's `probe.url` matches `google.com/sorry/` or `accounts.google.com` →
    `blocked` is set to that URL. **This stops the whole run** (the outer
    `while queue and not blocked` loop exits) even if other batches were
    queued. I would not queue a retry batch after this — I'd stop, tell the
    user exactly which URL it hit, that only a person can clear it inside
    the Aside browser, and that everything saved so far is kept.
  - Row's `ok` is false → `status = Failed`, `last_error` set from
    `describe_failure(row.kind)` (no-box / not-sent / not-typed / no-image /
    download / exception / cut-off / no-time, per the §7 table). Row is added
    to this batch's `failed` list.
  - Row's `ok` is true but its downloaded file is missing from
    `artifacts/` → `Failed`, `last_error` names the missing path. Added to
    `failed`.
  - Row's file hash is already in `seen{}` (matches one of the 2 pre-existing
    `Generated` images, or an earlier row in this same run) → `Failed`,
    `last_error = "identical to <other file> — tab isolation broke;
    resubmit"`. Added to `failed`. The new file is not written.
  - Row's saved width/height ratio is off by more than 4% from its
    `aspect_ratio` → the just-written file is deleted, its hash removed from
    `seen`, `status = Failed`, `last_error` names the actual size and asked
    ratio, calling it "likely another row's image; resubmit". Added to
    `failed`.
  - Otherwise → file is kept at `<out>/<filename>`, `status = Generated`,
    `last_error` cleared, `saved += 1`, manifest written back immediately
    (so an interruption after this point keeps this row). If the saved
    file's long edge is ≤1024px, its filename is also appended to a
    `previews` list — status is still set to `Generated`, but this is the
    "preview instead of original" case SKILL.md §5.4 calls out, and I treat
    that `**` log line as something to hand back to the user even though the
    row nominally succeeded.
  - Each save is logged with dimensions, measured ratio, byte size, and
    per-stage timing — I'd relay the summary line, not every field.
- Batch ends with `batch of 4: <saved> saved in <Ns>, all tabs closed` — every
  tab this call opened is closed in the JS `finally`, success or failure.

**Retry branch**: back in `main()`, after a non-retry batch, its `failed`
list is folded into a running `retry` list. If the queue is now empty and
`retry` is non-empty, the script logs `N row(s) failed; trying them once
more`, re-plans `retry` into fresh batch(es) marked `is_retry=True`, and the
outer loop picks them up exactly like Step 2 above — **except** a row that
fails again on this second pass is *not* re-queued (`if not is_retry: retry
+= failed` — only first-pass failures get the one retry). So, concretely for
this scenario:

- **Branch — all 4 succeed on the first batch**: `retry` stays empty, queue
  is empty, loop ends after one batch. No retry batch runs.
- **Branch — some of the 4 fail on the first batch (not blocked)**: those
  specific rows are re-sent once as a second, smaller batch. Whatever is
  still `Failed` after that second batch is left `Failed` for this run — I
  do not send a third attempt myself; that's the script's contract, and
  SKILL.md §3 says re-running the same command is how a caller retries again.
- **Branch — a challenge/sign-in wall is hit on the first batch**: no retry
  batch is planned at all; the run stops immediately per (c) above.

## Step 3 — After the run loop exits

- If `blocked` was ever set: log the "stopping: the page went to …" message
  (§4/§7). I relay this verbatim plus "clear it in the Aside browser by
  hand, then re-run the same command — finished rows are kept."
- Otherwise, final summary line: `saved <N> this run · manifest <T>/7 ·
  <S>s elapsed`, where `T` is the count of all `Generated` rows across the
  whole manifest (the 2 pre-existing ones plus however many of the 4
  `Failed` rows made it through this run).
- If `previews` is non-empty: the `** K row(s) saved at the 1024px preview
  size instead of the original: <names>` line. I relay this and tell the
  user those specific rows need a deliberate re-do — per §3, redoing a row
  that already reads `Generated` means setting its `status` back to `Failed`
  in the manifest first, since the script only ever picks up `Pending`/
  `Failed` rows.
- `left = filenames still Pending/Failed` after everything above:
  - **Branch — `left` is empty**: script returns normally (exit code 0). I
    tell the user all 4 targeted rows are now `Generated` (files exist,
    manifest total `T`/7), the 2 pre-existing `Generated` rows were left
    alone, and the 1 `Needs-Manual` row is still waiting on them — the
    script never touches it.
  - **Branch — `left` is non-empty**: script logs `N row(s) still
    Pending/Failed with last_error set; re-run the same command to retry
    only those` and exits with code `2`. I relay that count, name each
    remaining row and its `last_error` (mapped through the §7 table to a
    concrete next step — e.g. a `no_box`/`not_sent` cluster means "open
    Gemini in Aside by hand and check for a dialog over the prompt box"; a
    repeated "another row's download" means shortening `--batch`), and tell
    the user re-running the identical command is enough — it will only
    resubmit what's still `Pending`/`Failed`, not the rows already
    `Generated`.

## Step 4 — Verification before reporting success (SKILL.md §5)

Only for rows this run actually turned `Generated` (skip the 2 pre-existing
ones and the still-`Needs-Manual` row, unless spot-checking):

1. Confirm each of those rows reads `Generated` in the manifest and its file
   exists — already implied by Step 3's branches, re-check by reading
   `<manifest>` back.
2. Ratio already enforced during the run (4% tolerance, §5 says verify
   dimensions too) — re-derive width/height from the saved files and compare
   against each row's `aspect_ratio` as a second check.
3. No two output files share a checksum, across the full set including the
   2 pre-existing ones (the run's own `seen{}` guard should have already
   prevented this, but SKILL.md says check anyway):

   ```bash
   shasum -a 256 <out>/*.png | awk '{print substr($1,1,12), $2}' | sort
   ```

4. No file is 1024px on its long edge — covered by the `previews` warning in
   Step 3; an absent `**` line is the pass, so I don't need a second scan
   unless that line appeared, in which case I already flagged it above.
5. No Gemini tab left open in the Aside browser — the JS `finally` block
   closes every tab it opened, on every exit path (success, per-row failure,
   or thrown exception). I'd only re-check this by hand if the run itself
   reported something inconsistent with a clean finish (e.g. branch (a) or
   (b) in Step 2, where the call was cut off before printing its own
   completion).

## What I tell the user, end to end

1. Before running: which precondition check failed, if any (Step 0), and stop
   there — no run attempted.
2. Right after the script starts: "4 Failed row(s) picked up in 1 batch; the
   2 already-Generated rows and the 1 Needs-Manual row are left alone."
3. Per batch, if anything failed: which filenames and why (from
   `last_error`, in plain terms via the §7 table), and whether that failure
   will be retried automatically within this same run or not.
4. If blocked: stop, name the URL, say only a person can clear it in Aside,
   confirm finished rows are kept.
5. At the end: final counts (`saved this run` / `manifest T/7`), any
   preview-size rows that need a deliberate re-do, and — if `left` is
   non-empty — that re-running the identical command retries only what's
   still outstanding, with the specific reason for each.
6. Always: the 1 `Needs-Manual` row is the user's own file to add: this
   skill never submits it and never will.
