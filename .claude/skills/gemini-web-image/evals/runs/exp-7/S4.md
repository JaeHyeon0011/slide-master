# S4 — 3-row manifest, row 3's ratio line contradicts its `aspect_ratio` field

## Scenario recap

- 3-row manifest.
- Row 2: `prompt` already opens with `Generate a 16:9 image (aspect ratio exactly 16:9).`; `aspect_ratio` = `16:9`. Line and field agree.
- Row 3: `prompt` opens with the *same* `Generate a 16:9 image (aspect ratio exactly 16:9).` line, but `aspect_ratio` = `1:1`. Line and field disagree.
- Row 1: unspecified — treated below as a clean row (no embedded ratio line, normal `aspect_ratio`).

Traced against `with_ratio()` in `scripts/gemini_web_image.py`:

- **Row 2**: `lead = "Generate a 16:9 image (aspect ratio exactly 16:9).\n\n"`. `prompt.lstrip().startswith(lead.strip())` is `True`, so `with_ratio` returns the prompt **unchanged** — no duplicate line, no warning. This is the tolerated no-op path, not an error.
- **Row 3**: `lead = "Generate a 1:1 image (aspect ratio exactly 1:1).\n\n"`. The prompt starts with the 16:9 line, not the 1:1 line, so the unchanged-path check fails. `RATIO_LINE_RE.match()` then finds the stale `16:9` line, sees it disagrees with the row's own `1:1`, logs `**   prompt opens with a 16:9 ratio line but the row asks for 1:1; sending the row's ratio in front of it`, and returns `lead + prompt` — i.e. it **prepends** a second, correct `1:1` line in front of the existing (now stale) `16:9` line. The text actually sent to Gemini for row 3 will carry **two contradicting ratio instructions** back to back. The script reports this; it does not remove the stale line (SKILL.md §4: *"The manifest's prompt must not carry that line itself; it is added only if missing, and a line naming a different ratio is reported"* — reported, not corrected).

That contradiction is a manifest-authoring defect, not a script bug, and it is the one decision point this plan turns on.

## Before the run

1. **Preconditions (SKILL.md §2), in order, stop and name the first one that fails:**
   ```bash
   aside --version
   ```
   Confirms the Aside CLI is on PATH (or under `~/.local/bin` / `%LOCALAPPDATA%\Aside\CLI\current` per `find_aside()`).
   - Confirm the Aside app process is running — a closed app fails every `aside repl` call.
   - Open `gemini.google.com/images` in the Aside browser and confirm the prompt box renders (Aside has its own browser profile; a Chrome sign-in does not carry over).
   - Confirm the manifest path exists and has at least one `Pending`/`Failed` row:
     ```bash
     python3 -c "import json,sys; d=json.load(open(sys.argv[1])); print([ (i,it['status'],it['aspect_ratio']) for i,it in enumerate(d['items'])])" projects/<name>/images/image_prompts.json
     ```
   If any of these fail, stop and name the failed precondition — do not fall back to another image path from inside this skill (that decision belongs to the caller).

2. **Read all 3 rows' `prompt` + `aspect_ratio` before submitting anything**, and mentally (or with a throwaway script) run each one through `with_ratio()`'s logic, because a contradiction caught now is free and a contradiction caught after submission has already spent one Gemini generation and one of the batch's tab slots.
   - Row 1: no embedded ratio line → `with_ratio` will prepend it cleanly. No action.
   - Row 2: embedded line matches `aspect_ratio`. No action — this is the tolerated no-op path, not a defect, so it is **left untouched**.
   - Row 3: embedded line (`16:9`) contradicts `aspect_ratio` (`1:1`). **This is the decision point.**

3. **Decision point — row 3's contradiction:**
   - *Branch taken:* treat `aspect_ratio` as the authoritative field (it is the structured value both this script and `image_gen.py` key off under the shared manifest contract; the embedded sentence is exactly the boilerplate `with_ratio()` itself generates, so a leftover/wrong copy of it in the source JSON reads as stale text rather than a considered instruction) and **fix the manifest before running**: strip the stale leading line — `Generate a 16:9 image (aspect ratio exactly 16:9).` plus the blank line after it — from row 3's `prompt`, leaving the rest of the prompt body and `aspect_ratio: "1:1"` untouched. This makes row 3 take the same clean "line was missing, add it once" path row 1 takes, and removes the need to rely on the script's stale-line special case at all.
   - *Rejected branch:* run row 3 as-is and let the script's own guardrails absorb it — the `**` log line documents the mismatch, and if Gemini's output ends up outside 4% of `1:1` the post-download ratio check (§4 "Treat a wrong aspect ratio as a failed row") deletes the file and marks the row `Failed`. Rejected because: (a) it burns a generation + a batch tab slot on a prompt already known to be self-contradictory, and (b) the run's one automatic retry pass would resend the *identical* contaminated prompt, so a failure here is not transient — it would very likely fail the same way twice and still need a manual fix afterward. Fixing it up front costs nothing and avoids a guaranteed-or-likely wasted cycle.
   - *If I could not tell which side was authoritative* (e.g. the field itself looked like it could be the typo, not the prompt line) I would not silently pick one — I'd surface the conflict and ask before running, rather than guess. Here the field is treated as authoritative for the reason above, so no question is needed.

4. **What I tell the user before running:**
   > Row 3's prompt already opens with a 16:9 ratio line, but its `aspect_ratio` field says 1:1 — the script only logs that kind of mismatch, it doesn't fix it, so as written it would hand Gemini a prompt asking for two different ratios in the first two lines. I removed the stale 16:9 line from row 3's prompt (kept `aspect_ratio: 1:1` as-is, since that's the field the rest of the pipeline reads). Row 2 is fine as-is — its embedded line already matches its own `aspect_ratio`, which the script treats as a no-op, not an error. Running all 3 rows now as one background batch; the Aside window can stay covered or minimized, you don't need to switch to it except that its tabs will flicker as each download lands.

## During the run

5. **Command (all 3 rows fit one batch — `MAX_BATCH` is 4):**
   ```bash
   python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
     --manifest projects/<name>/images/image_prompts.json
   ```
   (Windows: same call with `python` and backslashes; nothing else changes.) No `--batch`/`--deadline` override needed for 3 rows against the 420s default.

6. **What the script does, and the branch it's expected to take at each point:**
   - `find_aside()` locates the CLI; `main()` loads the manifest and filters to `RETRYABLE = {"Pending", "Failed"}` rows — all 3, assuming none are already `Generated`/`Needs-Manual`.
   - `plan_batches(pending, size=4)` builds each candidate batch's JS via `build_batch_js` and measures it with `subprocess.list2cmdline` against `ARG_LIMIT` (30,000 chars, the Windows command-line ceiling headroom). With 3 ordinary-length prompts this stays under the cap, so **all 3 rows land in a single batch**; only if a prompt is unusually long would `plan_batches` split it, in which case the run naturally becomes 2 `aside repl` calls instead of 1 — no different handling needed, the loop below just iterates twice.
   - Log line: `3 row(s) in 1 batch(es) of up to 4; the Aside window can stay covered or minimized while it runs`.
   - `run_batch()` builds `jobs = [{"out": "row0.png", ...}, {"out": "row1.png", ...}, {"out": "row2.png", ...}]` — note these `rowN.png` names are the batch's own index, not the manifest's row numbering, so when reading the log the *first* job in the batch is manifest row 1, not necessarily anything called "row 1" elsewhere.
   - One `aside repl` subprocess call carries the whole JS payload as a single argument (`run_js`, timeout `REPL_LIMIT + 30` = 150s wall clock on the Python side; the JS budgets itself to 105s and returns before the REPL's own 120s hard limit).
   - Inside that call: opens 3 tabs with `openTab()` (never `aside "<url>"`, since a CLI-opened tab can't be closed from the REPL), never brings any tab or the window forward, types each row's `with_ratio()`-processed prompt via `keyboard.insertText()` (falling back to `execCommand('insertText')` if under 10 chars landed), submits with Enter then the send-button icon as fallback, confirms "started" via a `model-response` element or the URL moving to `/app/<id>`, and staggers 0.7–2.0s of jitter between sends (§4: "a human does not send four prompts on a metronome").
   - Then, one at a time as each row's download button appears (`ready()`): `bringToFront()` that row's own tab (the only focus-touching step, and only inside the Aside window), click the download icon, wait on the download event, read `download.path()`, write the bytes to `artifacts/`, sleep 1.5s, close that tab. A download whose filename was already seen this batch is treated as another row's file handed over again and re-clicked, not saved.
   - Every opened tab is closed in `finally`, success or failure.
   - Back in Python, per row: not-`ok` → `Failed` with `describe_failure()`'s message; else sha256-dedupe against `seen` (this run's saves plus anything already `Generated` on disk) → collision marks `Failed`, `"identical to <file> — tab isolation broke; resubmit"`; else write the file, compare its measured aspect ratio to the row's `aspect_ratio` within 4% → **outside tolerance deletes the file and marks `Failed`** (`"saved WxH but the row asks for ... — likely another row's image; resubmit"`), inside tolerance marks `Generated`, clears `last_error`, and counts it saved. `save_manifest()` runs after every single row, so a crash mid-batch keeps whatever already landed.
   - **Row 2's expected branch**: single clean 16:9 line sent, generation ~2752×1536, ratio check passes (~1.792 vs target 1.778, within 4%) → `Generated`.
   - **Row 3's expected branch**: because it was pre-fixed in step 3, it now sends a single clean 1:1 line, generation ~2048×2048, ratio check passes (1.0 vs 1.0) → `Generated`. (Had it been left unfixed, the two most likely outcomes were: the model honors the *first* line — the prepended 1:1 — and the row passes by luck; or it produces something the 4% check rejects, e.g. anything reading as 16:9-ish, and the row is deleted and marked `Failed` with the generic "likely another row's image" message even though the real cause was the contradictory prompt, not a mis-attributed download.)
   - **Row 1's expected branch**: no ratio-line involvement at all, ordinary success path.
   - If any row in this first pass fails, `main()`'s loop collects it into `retry`, re-batches just the failed subset with `is_retry=True`, and issues one more `aside repl` call automatically before the run ends — I do not need to intervene for this, it's already inside the single command from step 5.

7. **Branches that would make me stop and act mid-plan (not expected here, but the ones the skill calls out):**
   - `blocked` gets set (page went to `google.com/sorry/...` or `accounts.google.com`) → the run stops itself immediately, finished rows are kept. I do not retry blindly; I tell the user this needs a human to clear the challenge or re-sign-in inside the Aside browser, then rerun the exact same command — it's idempotent, only the still-`Pending`/`Failed` rows are resent.
   - The whole call comes back "aside repl returned no result ... isn't running" → check whether the Aside app is actually closed vs. the call simply ran past 120s; if it recurs with the app open, drop `--batch` to 3 or 2 on the rerun (irrelevant here at 3 rows unless it recurs, in which case I'd try `--batch 2`, giving batches of 2+1).
   - `deadline` reached before all batches start → log names how many rows are left unsent; rerun the same command to pick them up (only relevant on much larger manifests than 3 rows against a 420s default).

## After the run — verify before reporting success (SKILL.md §5)

1. All 3 rows read `Generated` and each row's file exists on disk.
2. Each file's measured ratio is within 4% of its row's `aspect_ratio` (row 2 ≈ 16:9, row 3 ≈ 1:1 given the pre-fix).
3. No two of the 3 output files share a checksum:
   ```bash
   shasum -a 256 projects/<name>/images/*.png | awk '{print substr($1,1,12), $2}' | sort
   ```
4. No file is 1024px on its long edge (that's the inline preview, not the original) — the run's own `**` preview-size log line is the check; its absence is the pass.
5. No Gemini tab is left open in the Aside browser.

**What I tell the user after the run:**
- Saved/failed counts and elapsed time (from the script's own summary log line).
- Confirmation that steps 1–5 above all passed, or the specific row/check that didn't.
- If row 3 is *still* `Failed` after this run's built-in retry with a ratio-mismatch `last_error`, that is now a real, not a contradiction-caused, ratio issue (the stale line was already removed pre-run) — I'd treat it like any other failed row per SKILL.md §7's table rather than assume it's the stale-line case again, and would not touch the manifest a second time without first reading that `last_error` text.
