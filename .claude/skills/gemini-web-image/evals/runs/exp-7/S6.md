## 1. Classify the error before doing anything else

The row's `last_error` is:

```
gemini-web: prompt box never appeared at https://www.google.com/sorry/index?continue=...
```

This string is built by `describe_failure()` for `kind == "no_box"`
(`scripts/gemini_web_image.py:479-480`): the batch JS waited up to 25s for the
prompt-box locator to attach (`gemini_web_image.py:319`), it never did, and the
row's `probe.url` was recorded as whatever page the tab was actually on
(`gemini_web_image.py:320`).

**Decision point 1 — read the URL, per SKILL.md §7's `prompt box never appeared at <url>` row:**

- URL matches `google.com/sorry/` → Google's automated-traffic challenge. **This branch.**
- URL matches `accounts.google.com` → signed-out session (sign-in wall). Not this case.
- Any other, normal Gemini URL → the page's structure changed; re-read it with
  `aside repl` + `snapshot()` before touching selectors. Not this case.

The given URL is `https://www.google.com/sorry/index?continue=...`, which matches
`CHALLENGE_RE = re.compile(r"google\.com/sorry/|accounts\.google\.com", re.I)`
(`gemini_web_image.py:84`) on the first branch. So per SKILL.md §4 ("Stop on
`google.com/sorry/` or a sign-in page ... Only a person can clear it in the
Aside browser; the run stops and keeps what it finished") and §7, this is
Google's unusual-traffic interstitial, not a selector or Aside-availability
problem.

**Decision point 2 — do I need to check Aside itself (§2 preconditions /
`aside repl returned no result` row)?** No: the batch produced a real
`ASIDE_RESULT`/`ASIDE_ROW` with a probed page URL, which only happens if
`aside repl` ran and returned normally. That rules out "Aside app closed" or
"call ran past 120s" — those fail differently (`aside repl returned no
result (... isn't running ...)`, `gemini_web_image.py:519-528`). I do not run
`aside --version`, do not reopen the Aside app, and do not reinstall Aside.

## 2. Confirm the run's actual state (read-only)

```bash
cat projects/<name>/images/image_prompts.json
```

(or open it) and check, for every item:

- Which rows show `"status": "Failed"` with this exact `last_error`, vs. rows
  that already show `"status": "Generated"`.

This matters because the script's own stopping behavior
(`gemini_web_image.py:702-705`, `run_batch`'s `blocked` return) means: once one
row in a batch probes to a challenge URL, that batch's *other* rows are still
finished and their JSON is written back row-by-row inside `run_batch`
(`save_manifest(...)` is called per row, `gemini_web_image.py:612,614`), and no
further batch is started (`while queue and not blocked`,
`gemini_web_image.py:685`). So:

- `Generated` rows in the manifest are real, finished images — never resend
  these.
- `Failed` rows (this one and any others in flight when the challenge hit)
  are what's left to redo.

No command changes anything in this step; it's just establishing scope before
messaging the user.

## 5. Rerun — exact command

Same manifest, same defaults as the original run (no flags are changed by this
recovery — nothing in §4/§7 calls for a different `--batch` or `--deadline`
here):

```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/<name>/images/image_prompts.json
```

(Windows: `python` in place of `python3`, backslashes in the path — §3, no
other change.)

This is safe to rerun as-is because the script is idempotent
(`RETRYABLE = {"Pending", "Failed"}`, `gemini_web_image.py:57,659`): it only
resubmits rows still `Pending`/`Failed`; `Generated` rows are skipped, and the
`seen` dict is pre-seeded from files already on disk
(`gemini_web_image.py:673-677`) so a rerun can't save a duplicate of a row
that finished earlier.

After the process exits, check its exit code.

## 6. Decision point 4 — result of the rerun

- **Exit code `2`**, and the tail of the log does **not** contain another
  `stopping: the page went to ...` line → some rows are still
  `Pending`/`Failed` for an unrelated reason. Read each such row's new
  `last_error` from the manifest and look it up in SKILL.md §7's table (e.g.
  `not_sent`, `no_image`, a download failure, ...) and follow that row's

- **Exit code `2`**, and the log again shows `stopping: the page went to
  https://www.google.com/sorry/...` → the challenge recurred. Do not change
  `--batch`, do not add retry loops, and do not edit the script — nothing in
  §4/§7 attributes a repeated `google.com/sorry/` block to a script parameter.
  Go back to §3 and tell the user plainly that it happened again after they
  ccleared it once, so they know before clearing it a second time. Per §2
  ("Do not fall back to another image path from inside this skill — that
  decision belongs to the caller"), if this keeps recurring I hand it back to
  the caller (the ppt-master pipeline / the user) rather than silently
  switching to a different image backend myself.
- **Exit code `1`** (`aside` CLI not found) → this would be a different,
  unrelated failure surfaced at start-up (`gemini_web_image.py:648-653`); not
  expected here since Aside was working moments ago, but if seen, follow that
