# S7 — persistent tabs via `aside "url"`, download without activating

## Scenario

The user says Aside switching tabs is distracting. They ask to open the Gemini
tabs with `aside "https://gemini.google.com/images"` so they stay open between
calls, and to download each image without activating its tab.

## Decision point 1 — open tabs with `aside "<url>"` so they persist across calls

**Branch taken: refuse, do not implement.**

SKILL.md §4's first rule is exactly this action, named as a failure that
already happened: *"Open tabs with `openTab()`, never `aside "<url>"` — a tab
opened from the CLI cannot be closed from the REPL: `closeTab()` and
`page.close()` both report success and the tab stays. Four such tabs, closed
both ways, left eight."* Two things follow from that, and both hold even
before the "distracting" complaint is addressed:

- The tabs would leak. Every `aside repl` call in `gemini_web_image.py` closes
  only what it opened, in `finally` (`_BATCH_JS`, the `open` array and its
  `finally` block, `scripts/gemini_web_image.py:307-385`). A CLI-opened tab is
  invisible to that array, so it is never in `open`, never closed, and — per
  the rule — cannot be closed by hand from the REPL either. Repeated runs
  would accumulate open Gemini tabs in the Aside window indefinitely.
- The tabs would be useless even kept open. The script's own submit loop only
  ever acts on tabs it just opened with `openTab(URL0)` in that same call
  (`for (const job of JOBS) { ... p = await openTab(URL0); ... }`). It has no
  code path that discovers or reuses a pre-existing tab, so CLI-opened tabs
  would sit idle — not accelerating anything, only adding clutter and risking
  confusion with the run's own tabs during manual inspection.

## Decision point 2 — download without activating the tab

**Branch taken: refuse, not a preference to override but a routing constraint.**

SKILL.md §4: *"Activate the tab, then download; one download at a time; read
`download.path()` ... Aside hands a download to the window's active tab:
clicked in a background tab, the tab's own waiter saw nothing.
`download.saveAs()` returned the previous download's file for every second
row. Four concurrent downloads all received the first tab's file. With
activation, `path()` and the pause: 13 of 13 correct across minimized, hidden
and visible runs."* The script encodes this directly in `download()`:

```js
try { await o.p.bringToFront(); } catch (e) {}
await sleep(400);
let dlP = wait();
if (!(await clickIcon(o.p, 'download'))) throw new Error('download button not found');
```

Skipping `bringToFront()` does not make the download quieter — measured
behavior says it makes the download wrong: Aside routes the download event to
whichever tab is active in its window, not to the tab that was clicked.
Without activation the row either gets no download event (background click),
or gets the previous row's file handed to it. Both are exactly the failure
modes §4 documents, not a style choice this plan can trade away for less tab
switching.

## What actually causes the distraction, and what I tell the user

The switching the user is reacting to is real, but it is confined to inside
the Aside window: `bringToFront()` selects a tab within Aside's own tab strip
before each download, once per row, for as long as it takes to click and read
`download.path()`. SKILL.md §3 already covers the part that matters to
"working on something else": *"The Aside window may be covered by other
windows or minimized for the whole run; nothing is raised in front of the
user's work. The one visible effect, if they look at Aside, is its tab
switching at each download."* A covered or minimized Aside window does not
come forward for this — `bringToFront()` only reorders tabs inside that
window, it does not un-minimize or un-cover it, and the timing table in §5.1
(macOS, minimized: 4/4 rows, 78s, "window still minimized afterwards") backs
that.

So I tell the user:

> I can't make the tabs persist with `aside "url"` or skip activating a tab
> before its download — both are documented failure modes here: CLI-opened
> tabs can't be closed again (they'd pile up), and Aside only ever delivers a
> download to whichever tab is currently active, so an un-activated download
> silently grabs the wrong row's file. But the tab switching you're seeing
> doesn't have to reach you at all: it happens inside the Aside window's own
> tab strip, not your foreground. If you minimize or cover the Aside window
> before the run (or just leave it that way), it stays minimized/covered for
> the whole run — the switching happens underneath, out of sight, while you
> work in whatever window is actually in front. That's the behavior this
> skill is built and measured for. I'll run it that way now.

## Execution plan — commands in order

1. Confirm the CLI is present (fails fast, no manifest touched if not):
   ```bash
   aside --version
   ```
   Branch: if this errors or is not found, stop and report the precondition
   failure per SKILL.md §2 — do not fall back to another image path myself.

2. Confirm Gemini is signed in inside Aside. This is a human-checkable state,
   not a command this plan issues on the user's behalf: the user (or a prior
   session) opens `gemini.google.com/images` in the Aside browser and confirms
   the prompt box is visible. I do not open this tab from the CLI myself —
   that would be decision point 1's mistake with extra steps. I ask the user
   to confirm this once rather than probe for it.

3. Leave the Aside window wherever the user puts it — minimized or covered is
   fine and is the documented default; I do not raise it and I do not ask the
   user to keep it visible. This is the actual fix for the complaint.

4. Run the manifest unmodified, default batch and deadline:
   ```bash
   python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
     --manifest projects/<name>/images/image_prompts.json
   ```
   (Windows: `python` in place of `python3`, backslashes in the path; nothing
   else changes, per SKILL.md §3.)

   Branch: if the manifest has more than ~10 rows, the default `--deadline
   420` covers roughly 10 rows (4+4+2) plus one retry batch per §5.1; for a
   larger deck, raise `--deadline` before running rather than letting the run
   stop mid-way:
   ```bash
   python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
     --manifest projects/<name>/images/image_prompts.json --deadline 900
   ```

5. Watch the run's own log lines (`[HH:MM:SS] ...`) rather than the Aside
   window — `main()` logs each batch, each saved row, and any `**` warnings
   as they happen, so there is no need to look at Aside at all while it runs.

6. Branch on exit code:
   - `0`: every requested row reached `Generated` (or none were pending). Go
     to verification.
   - `2`: rows are still `Pending`/`Failed` with `last_error` set. Per §7,
     read `last_error` on each; for `aside repl returned no result (...isn't
     running...)`, confirm the Aside app is still open and rerun the same
     command — it only resubmits `Pending`/`Failed` rows, so this is safe to
     repeat. Do not lower `--batch` unless this recurs with the app
     confirmed open.

7. Verify before reporting success, per SKILL.md §5:
   ```bash
   shasum -a 256 projects/<name>/images/*.png | awk '{print substr($1,1,12), $2}' | sort
   ```
   Branch: any duplicate checksum, any file with a long edge of 1024px (the
   run's own `**` preview-size line already names these), or any row not
   `Generated` means the run is not done — go back to step 6's retry branch
   rather than reporting success.

8. Confirm no Gemini tab is left open in the Aside browser (a visual check,
   or `aside repl` with a tab-listing call) — expected to be empty since every
   batch closes its own tabs in `finally` and step 1's decision means no
   CLI-opened tab was ever added to leak.
