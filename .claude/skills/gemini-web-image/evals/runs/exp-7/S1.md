# Scenario S1 — 6-row manifest (4×16:9, 1×4:3, 1×1:1), Aside running & signed in

Authority: `SKILL.md` and `scripts/gemini_web_image.py` only. Plan, not a transcript
— nothing below was executed.

Assumed working directory: the `slide-master` repo root (manifests are addressed
relative to it, matching the `--manifest` examples in SKILL.md §3).
Manifest: `projects/demo/images/image_prompts.json`, 6 items, all `status: "Pending"`,
`aspect_ratio` four `16:9`, one `4:3`, one `1:1`.

---

   - **Branch — not found / errors**: STOP. Tell the user: "Aside CLI isn't on
     PATH. Install it (macOS/Linux: `curl -fsSL https://releases.aside.com/install.sh
     | bash`; Windows PowerShell: `irm https://releases.aside.com/install.ps1 | iex`),
     open the Aside app, sign in to Gemini there, then tell me to retry. The
     manifest is untouched." Do not fall back to another image path myself —
     that decision belongs to the caller (SKILL.md §2).
   - **Branch — found**: continue. (The scenario states the Aside app is
     running, so I take this branch.)

2. Gemini sign-in inside Aside. SKILL.md §2 names the manual check ("open
   `gemini.google.com/images` in the Aside browser; a signed-in page shows the
   prompt box"), but the scenario already states the browser is signed in, and
   the script's own run is the real test of this (a sign-in wall is caught by
   `CHALLENGE_RE` mid-run, §3 below). I do not spend a separate call proving
   this ahead of time; I take the "signed in" branch as given and let the run
   itself fail fast if that's wrong.

3. Validate the manifest before touching it:
   ```
   python3 -c "import json; d=json.load(open('projects/demo/images/image_prompts.json')); [print(it['filename'], it['status'], it['aspect_ratio']) for it in d['items']]"
   ```
   - **Branch — 0 rows with status Pending/Failed**: STOP, nothing to do
     (matches `main()`'s own "nothing to do" branch). Not taken here: expect
     6 lines, all `Pending`, ratios `16:9 ×4, 4:3 ×1, 1:1 ×1`.
   - **Branch — matches expectation**: continue to run.

**What I tell the user before running**: "Preconditions check out — Aside CLI

4, 420s deadline). This runs in the background — the Aside window can stay
minimized or covered while you do other things; the only visible motion, if
you look at it, is its tab switching at each download."

## 3. What the script does with these 6 rows — decision points

`find_aside()` succeeds (branch taken per §1.1). `pending` = all 6 items
(none are `Needs-Manual`, so none are skipped — SKILL.md §3 idempotent rule).

`plan_batches(pending, size=4)`: walks the 6 items in manifest order and caps
each batch at 4 items *and* under the 30,000-char Windows-argv limit. With
ordinary prompt lengths the char cap never bites here, so the split is purely
by count: **batch 1 = the first 4 Pending rows in manifest order, batch 2 =
the remaining 2.** Which ratios land in which batch depends on the manifest's
row order, which the scenario doesn't specify — the plan doesn't assume a
particular mix (e.g. "all four 16:9 together"); it's whatever order the 6
rows are already in.

`seen` (checksum de-dupe seed) is empty: no item is already `Generated` with a
file on disk.

Main loop, `while queue and not blocked:` — pops one `(batch, is_retry)` at a
time.

### Batch 1 (4 rows, is_retry=False)

- **Deadline check**: `time.time() + 120 > run_started + 420`? No, this is the
  first batch. Continue. (Branch not taken — would only trigger on a slow
  host; if it did, the script logs "deadline: N row(s) left unsent; rerun to
  take them" and stops the whole run there.)
- Log: `batch: <4 filenames>`.
- `run_batch()`: builds `jobs = [{"out": "row0.png", "prompt": with_ratio(...)}, ...
  "row3.png"]`. `with_ratio()` prepends `Generate a {ar} image (aspect ratio
  exactly {ar}).\n\n` to each row's prompt **unless the prompt already opens
  with exactly that line for that row's own ratio**.
  - **Branch — prompt already opens with a *different* ratio's line** (e.g. a
    `4:3` row whose prompt text starts with the 16:9 sentence): logged as a
    `**` warning and the row's own ratio line is sent in front of it anyway
    — not treated as fatal, just flagged. Not expected in this manifest but
    the plan accounts for it.
  - **Branch — no ratio line present**: the normal case; the line is added.
- One `aside repl` call runs the batch JS (`run_js`, 150s subprocess timeout
  against a 105s in-JS budget). Inside that one call, for each of the 4 jobs,
  none brought to the front, nothing waited on paint:
  1. `openTab('https://gemini.google.com/images')` — **branch: throws** → row
     marked `kind: 'open'`, its error kept, loop continues to the next job
     (one row's open failure doesn't stop the batch).
  2. Wait for the prompt box (`rich-textarea .ql-editor` /
     `[contenteditable="true"]`) `attached` within 25s — **branch: timeout**
     → `kind: 'no_box'` + a page probe (URL + first 600 chars of body text);
     this is the branch a signed-out session or a Google "unusual traffic"
     interstitial falls into.
  3. Click + focus the box, `keyboard.insertText(prompt)`; if the box's typed
     length is still under 10 chars, fall back to
     `execCommand('insertText', …)`. **Branch: still under 10 chars after
     both** → `kind: 'not_typed'` + probe.
  4. Submit: try Enter, poll `started()` (a `model-response` element exists,
     or the URL has moved to `/app/<hex>`) every 500ms up to 10s; if not
     started and time remains, try clicking the send button (icon
     `arrow_upward`) and poll again. **Branch: neither works** →
     `kind: 'not_sent'` + probe — "a click is not proof of a send"
     (SKILL.md §4).
  5. On success: `r.sent = true`; sleep a randomized 700–2000ms before the
     next job opens its tab — deliberately uneven, "a human does not send
     four prompts on a metronome."
  - After all 4 jobs are attempted (opened, or failed at whichever step),
    the wait/download phase starts: poll every sent tab's `ready()` (a
    `model-response` whose scope contains a button with icon `download`)
    once a second, while time-left exceeds 22s (`DL_MIN`, an original takes
    11–17s to download).
    - **Branch — a tab never becomes ready before `DL_MIN`**: marked
      `kind: 'no_time'` (if it *did* become ready but too late to start the
      download) or `kind: 'no_image'` (never ready at all) + probe. `no_image`
      with a `page ends with: …` tail usually means Gemini answered with text
      instead of an image — often a refusal of the prompt.
    - **Branch — ready in time**: `download()` runs — `bringToFront()` that
      tab (a tab switch inside the Aside window only; the window itself
      stays minimized/covered), a 400ms settle, then click the download icon
      and await the `download` event. **Branch — the clicked download's
      `suggestedFilename()` was already seen earlier in this same batch**:
      this is another row's file handed over again; retry the click up to 2
      more times, 2s apart. If still a repeat after that, the row fails with
      `'only received another row\'s download'` rather than being saved
      under a wrong name. Otherwise the file is read via `download.path()`,
      written to the session's `artifacts/row{i}.png`, and the tab pauses
      1500ms before the next download starts — downloads are strictly serial
      even though generation ran in parallel.
    - **Branch — download button never appears**: `kind: 'download'`,
      `'download button not found'`.
  - `finally`: every tab this call opened via `openTab()` is closed with
    `closeTab()`, on every branch above, success or failure alike — nothing
    from batch 1 is left open going into batch 2.
  - The call prints `ASIDE_DIR`, one `ASIDE_ROW` per row as it lands, and
    (if it didn't get cut off at the REPL's 120s hard limit) a final
    `ASIDE_RESULT` with the full `rows` map.

- Back in Python, `parse_result(out)`:
  - **Branch — no `ASIDE_RESULT` and no `ASIDE_DIR` at all** (e.g. the call
    timed out before printing anything, or Aside genuinely wasn't running):
    all 4 items in batch 1 are marked `Failed`, `last_error` = "gemini-web:
    aside repl returned no result (…)" (with an extra clause about the app
    being closed / the call exceeding 120s if that phrase matches), the
    manifest is saved, and `run_batch` returns `(0, "", batch1)` — the whole
    batch goes to retry, nothing saved yet.
  - **Branch — partial output only** (`ASIDE_DIR`/`ASIDE_ROW` lines present
    but the call was cut off before `ASIDE_RESULT`): `result['partial'] =
    True`; rows already reported as saved are kept; any job with no row at
    all is synthesized as `kind: 'cut_off'`.
  - **Branch — full result**: normal path, described next.

  For each of the 4 `(job, item)` pairs:
  - If the row's `probe.url` matches `CHALLENGE_RE`
    (`google.com/sorry/…` or `accounts.google.com`) → `blocked` is set to
    that URL. This is Google's unusual-traffic check or a signed-out session;
    **only a person can clear it**, so after this batch finishes processing
    its remaining rows, the outer `while queue and not blocked:` loop will
    not start batch 2 or any retry. Not expected here (scenario states the
    browser is signed in) — I don't take this branch, but the plan accounts
    for it: **if it fires, I stop, do not attempt batch 2, and tell the
    user**: "Stopping — the page went to `<url>`. That's Google's
    unusual-traffic check or a sign-in wall; only you can clear it inside the
    Aside browser. The rows already finished are kept — clear it and tell me
    to rerun for the rest."
  - If `row.get('ok')` is falsy → `item['status'] = 'Failed'`,
    `item['last_error'] = describe_failure(row)` (mapped from `row['kind']`
    per the table in SKILL.md §7), the item is appended to this pass's
    `failed` list, and logged as `  <filename>: <last_error>`.
  - If ok: locate the downloaded file at
    `<session_dir>/artifacts/row{i}.png` (or `<session_dir>/row{i}.png` as a
    fallback). **Branch — neither exists**: `Failed`,
    `"downloaded file missing at <path>"`.
    - Read the bytes, sha256 them. **Branch — digest already in `seen`**
      (another row in this run already saved these exact bytes — Aside
      handed the same file to two tabs): `Failed`, `"identical to <other
      filename> — tab isolation broke; resubmit"`. The file is **not**
      written to the output folder.
    - Otherwise write the bytes to `projects/demo/images/<item['filename']>`,
      read `(width, height)` from the PNG/JPEG header, compute
      `actual = width/height` against `target = aspect_ratio_value(item['aspect_ratio'])`.
      - **Branch — `target` is 0** (an `aspect_ratio` string that isn't
        `W:H`): kept as saved, but logged with a `**` note "ratio unchecked."
        Not expected here — all three ratios in the scenario are well-formed.
      - **Branch — `abs(actual - target) / target > 0.04`**: the file is
        **deleted** (`dest.unlink`), its digest removed from `seen`, and the
        item is marked `Failed`, `"saved WxHpx but the row asks for <ratio> —
        likely another row's image; resubmit"`. SKILL.md §4 is explicit this
        is treated as a failed row, never kept with a warning, because a
        mismatch this large almost always means a mis-routed download.
      - **Branch — within tolerance and `max(width, height) <= 1024`**: kept
        as `Generated`, but the filename is appended to a `previews` list —
        this is the 1024px inline-preview size, not the full original, and
        gets a `**` line in the final log even though the status is
        `Generated`.
      - **Branch — within tolerance and full-size**: kept as `Generated`,
        clean. `item.pop('last_error', None)`, `saved += 1`,
        `save_manifest()` immediately (so a crash right after this still
        keeps this row's progress on disk).
  - `save_manifest()` again after the loop (redundant safety write). Log:
    `batch of 4: <saved> saved in <T>s, all tabs closed`.

- Back in `main()`: `saved += got`. Since this was `is_retry=False`,
  `retry += failed` — whatever didn't save in batch 1 is queued for one more
  attempt after all first-pass batches have run, not immediately.

### Batch 2 (remaining 2 rows, is_retry=False)

Same procedure as batch 1, one level up: deadline check (still comfortably
inside the 420s budget — batch 1 measured around 80–120s per SKILL.md §5.1),
`run_batch()` with its own fresh `aside repl` call and its own fresh session
directory (the job `out` names restart at `row0.png`/`row1.png` inside that
session, but each success is copied straight out to its permanent
`item['filename']` in `projects/demo/images/`, so the reused generic names
never collide in the final output — only transient per-call artifacts share
them). Same branch tree as above applies independently to these 2 rows.
Any failures here are appended to the same `retry` list as batch 1's.

### Retry pass (only if `retry` is non-empty after both first-pass batches)

`queue` is empty once batch 2 is popped. **Branch — `retry` is empty** (all
6 rows saved clean on the first pass): the `if not queue and retry:` check is
false, the `while` loop ends here — this is the expected best case for this
scenario. **Branch — `retry` has 1+ items**: log `"<N> row(s) failed; trying
them once more"`, rebuild `queue = [(b, True) for b in plan_batches(retry, 4)]`
(a single batch, since at most 6 rows could ever be in `retry` and the cap is
4 — so a bad first pass could itself split into two retry batches, but at
most one retry *pass* happens regardless). These batches run with
`is_retry=True`, so this time `if not is_retry: retry += failed` is skipped —
**a row that fails again on retry is not queued a third time**; it simply
stays `Failed` with `last_error` set, to be picked up by a manual rerun later
(SKILL.md §3: "Failures retry once, in the same run… rerunning the same
command retries it again").

### End of run

`if blocked:` → not taken in the expected path; if it had fired, the log line
above is printed and the run stops with whatever subset finished.

`elapsed`, `total` (count of `Generated` items across the whole manifest — 6
if every row makes it) are logged: `"saved 6 this run · manifest 6/6 · <T>s
elapsed"`.

**Branch — `previews` non-empty**: log `"** <K> row(s) saved at the 1024px
preview size instead of the original: <names>"`. These rows are `Generated`
in the manifest but flagged — SKILL.md §5 point 4 says an *absent* `**` line
is the pass, so I do not accept these silently at the reporting stage (see
§4 below).

**Branch — any row still `Pending`/`Failed`** after the retry pass: log
`"<M> row(s) still Pending/Failed with last_error set; rerun the same command
to retry only those"`, exit code `2`. **Branch — none left**: script returns
normally, exit code `0`.

## 4. Verify before reporting success (SKILL.md §5) — commands, in order

Run regardless of the script's own exit code, as the final human-facing gate:

1. Re-read the manifest; confirm all 6 target rows now read `Generated` and
   their files exist:
   ```
   python3 -c "import json,os; d=json.load(open('projects/demo/images/image_prompts.json')); [print(it['filename'], it['status'], os.path.exists('projects/demo/images/'+it['filename'])) for it in d['items']]"
   ```
   - **Branch — any row is not `Generated` / file missing**: do not report
     success for that row; carry its `last_error` into the report to the
     user instead (see §5 below).

2. Independently re-check each saved file's ratio against its row's
   `aspect_ratio` (the script already enforces this at save time and removed
   any file that failed it, but SKILL.md §5 calls for checking the *final
   set* again, not trusting the save-time check alone).

3. Checksum de-dupe across the final set:
   ```
   shasum -a 256 projects/demo/images/*.png | awk '{print substr($1,1,12), $2}' | sort
   ```
   - **Branch — two files share a hash**: the script already refuses an
     exact duplicate mid-run (marks the later one `Failed`), so this should
     not happen on files that both read `Generated`; if it does anyway, that
     is itself a bug to report, not a row to silently accept.

4. Long-edge / preview-size check: none of the 6 files should have
   `max(width, height) <= 1024`. Cross-reference against whether the run's
   `**` preview-size line fired in §3 above.
   - **Branch — a row is flagged**: it is not a clean pass despite
     `status: Generated`. Set that row's `status` back to `Failed` in the
     manifest (SKILL.md §3: "Re-doing a row that already reads `Generated`
     means setting its status back to `Failed` first") and rerun the same
     `gemini_web_image.py` command — it will pick up only that row.
   - **Branch — no row flagged**: pass.

5. Confirm no Gemini tab is left open in the Aside browser. The script's
   `finally` closes every tab it opened on every code path (§3 above), so
   this is expected to already hold; I only check by hand if something
   external killed the `aside` process mid-call (outside the script's own
   try/finally).

## 5. What I tell the user

**All 6 clean on first pass (expected case given the stated preconditions)**:
"Done — all 6 rows generated: `<list of 6 filenames>`. Verified: each file's
aspect ratio matches its row within tolerance, all 6 checksums are distinct,
none is stuck at the 1024px preview size, and no Gemini tab is left open in
Aside. Files are in `projects/demo/images/`, and `image_prompts.json` is
updated to `Generated` for all six."

**Some rows failed the retry pass too**: "`<N>` of 6 rows generated. `<filename>`
failed twice: `<last_error>`. It's marked `Failed` in the manifest with that
error — rerun the same command to retry just it, or check SKILL.md §7 against
that error text first if it recurs."

**A preview-size file turned up in verification**: "`<filename>` saved but
only at the 1024px preview size, not the full original — not counting that as
a clean pass. I set its status back to `Failed` and reran to get the
original."

**Blocked by a sign-in wall / Google's challenge**: "Stopping — the page went
to `<url>`. That's Google's unusual-traffic check or a sign-in wall; only you
can clear it inside the Aside browser. Rows already finished are kept —
clear it and tell me to rerun for the rest."

**A precondition failed before any run started**: name the specific failed
precondition (Aside CLI missing / app not running / manifest has no
Pending-or-Failed rows) and stop there — never silently switch to a different
image-generation path (SKILL.md §2).
