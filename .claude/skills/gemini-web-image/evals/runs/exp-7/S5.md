# S5 — Execution plan: 4/4 rows Failed with "aside repl returned no result ... isn't running" while Aside is visibly open

## Scenario as given

- 4-row manifest, run through `gemini_web_image.py` with the default `--batch 4`
  (one `aside repl` call for all four rows).
- The Aside app is visibly open on the machine.
- All 4 rows come back `Failed` with
  `last_error: "gemini-web: aside repl returned no result (Aside isn't running on this machine ...)"`.

## Reading the failure before acting

`run_batch()` only writes this exact message when `parse_result(out)` returned
`None` — i.e. the `aside repl` call produced no `ASIDE_RESULT`/`ASIDE_ROW`
lines at all, not even a partial one. The code appends its own clarification
right there:

```python
why = first_error(out) or out.strip()[:200] or "no output"
if "isn't running" in why:
    why += (" — either the Aside app is closed, or the call ran past the "
            "REPL's 120s limit")
```

SKILL.md §4 says the same thing from the other direction: *"`aside repl` has
a 120s hard limit, and past it the CLI prints `Aside isn't running on this
machine` — which sends the reader to restart an app that is fine."* And §7's
table row for this exact string reads:

> Either the Aside app is closed or a call ran past 120s. Open the app and
> rerun; if it recurs with the app open, lower `--batch` to 3 or 2. Do not
> reinstall Aside for this.

So the message is known-ambiguous, and the scenario has already resolved half
the ambiguity for me: the app is open, so "the app is closed" is not the
operative branch. The remaining, more likely cause per the docs is a call
that ran past the REPL's 120s limit (all four rows in one `aside repl` call —
the docstring's own measurement is "97s against the JS budget of 105s", i.e.
normally fine but with little margin on a slow day). §7's prescribed fix for
that is lowering `--batch`, not touching the Aside install.

I will not reinstall or reconfigure Aside for this — §7 says so verbatim, and
nothing in the observed symptom (no result at all, not a probe URL, not a
sign-in wall, not a partial batch) points at the CLI-missing or
not-signed-in preconditions, which fail differently (CLI-not-found exits
before any manifest row is touched; a sign-in wall or challenge page shows up
as a `probe.url` on individual rows, which is not what we got here).

## Quick, side-effect-free precondition check first

Before touching `--batch`, confirm the two things SKILL.md ties to a healthy
run that a "visibly open" app doesn't by itself guarantee:

1. **Screen not locked.** §3: *"The screen must not be locked, and the Aside
   app must stay open."* A locked screen is easy to mistake for "the app is
   open" if it was open before the screen locked. I check whether the screen
   is currently locked and, if so, unlock it — this is not a code change and
   is not the `--batch` branch, so it comes first.
2. **Aside app is still the same running instance**, not a crashed/relaunched
   window that looks open. I don't have a documented CLI probe for this in
   either authoritative file beyond `aside --version` (Preconditions table,
   "Aside CLI installed" check) — that only proves the CLI binary resolves,
   not that the app side of the connection is alive. I will not invent a
   check beyond what's documented; if the screen is unlocked and the window
   looks open, I proceed to the rerun below and let the actual `aside repl`
   call be the real test.

Tell the user at this point: *"All 4 rows failed with Aside reporting 'isn't
running' even though the app is open. Per the skill doc, that message also
covers a call that simply ran past Aside's 120-second limit — it's not
necessarily telling us to restart anything. I checked the screen isn't
locked. I'm going to rerun once, unchanged, since the manifest is idempotent
and Failed rows are retried automatically — that tells us whether this was a
one-off timeout before I change anything."*

## Step 1 — plain rerun, unchanged

```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/<name>/images/image_prompts.json
```

(Windows: same command with `python` and backslashes in the path; nothing
else changes, per SKILL.md §3.)

This is safe to run as-is: `RETRYABLE = {"Pending", "Failed"}`, so all 4 rows
are picked up again automatically; nothing about the manifest needs editing
first.

**Decision point 1** — read the new `last_error` on each row after the run:

- **Branch A — some/all rows now read `Generated`.** The failure was the
  one-off "ran past 120s" case. Go to **Verification** below and report the
  counts to the user. Do not change `--batch` for future runs of this
  manifest; nothing here is a caller-facing setting per §3's flag table.
- **Branch B — rows are `Failed` again with the same
  `aside repl returned no result (... isn't running ...)` message.** This is
  "recurs with the app open" in §7's own words. Go to Step 2.
- **Branch C — rows are `Failed` with a *different* `last_error`** (e.g. a
  `probe.url` pointing at `google.com/sorry/...` or `accounts.google.com`, or
  `not_typed`, `no_box`, `download`, etc.). This is no longer the S5 scenario;
  I stop following this plan and instead read the matching row in SKILL.md
  §7's table for that specific message and act on that row's instruction
  instead (e.g. a challenge/sign-in URL needs a person to clear it in the
  Aside browser by hand — the script does not retry that on its own).

## Step 2 — lower `--batch` to 3

```bash
python3 .claude/skills/gemini-web-image/scripts/gemini_web_image.py \
  --manifest projects/<name>/images/image_prompts.json --batch 3
```

Tell the user: *"It recurred with Aside open, so per the skill doc this isn't
an app-restart problem — I'm lowering the batch size to 3 so each `aside
repl` call has more margin under the 120s limit."*

Four rows at `--batch 3` split into batches of 3 + 1 (`plan_batches`), so this
also changes the shape of the run, not just the size of one call.

**Decision point 2:**

- **Branch A — succeeds** (all rows now `Generated`, or at least the
  no-result failure is gone even if some rows fail for an unrelated,
  different reason). Go to **Verification**, report to the user, and note
  that `--batch 3` was needed for this run.
- **Branch B — same `... isn't running ...` message recurs again** on one or
  more rows. Go to Step 3.

**Decision point 3:**

- **Branch A — succeeds.** Go to **Verification**, report to the user.
- **Branch B — the same no-result failure still recurs at `--batch 2`.** This

## Step 4 — stop; do not improvise past what the docs cover

At this point three different batch sizes, with the Aside app open the whole
time, have all produced "aside repl returned no result ... isn't running".
Per the skill's own rules I stop here rather than guessing:

- **Do not reinstall Aside** — §7 says this explicitly for this exact error.
- **Do not drop `--batch` below 2** — the skill names 3 and 2 as the fix and
  no lower value; going below 2 is not a documented remedy and 1 was never
  measured for this failure mode.
- **Do not fall back to another image path from inside this skill** —
  Preconditions section: *"Stop and name the failed precondition. Do not fall
  back to another image path from inside this skill — that decision belongs
  to the caller."*
- **Do not touch the manifest by hand** beyond what the script already wrote
  — rows are already `Failed` with `last_error` set, which is the record the
  skill hands back to the caller (§7, last line: *"Rows this skill cannot
  finish stay `Failed`. Hand them back to the caller; the manifest is the
  record."*).

Tell the user: *"I tried the plain rerun and batch sizes 4 (the original
run), 3, and 2, all with the Aside app open and the screen unlocked, and every
attempt failed the same way: 'aside repl returned no result (Aside isn't
running on this machine ...)'. The skill's own docs say this message doesn't
distinguish 'app closed' from 'call ran over 120s', and I've ruled out the
closed-app case since Aside stayed open throughout, and ruled out the
locked-screen case. I'm not going to reinstall Aside or drop the batch size
further, since neither is what the skill documents for this. I also haven't
switched this manifest to a different image backend — that's your call, not
something this skill decides on its own. Two things worth you checking by
hand: (1) that the Aside app window is actually the live one and not a
stale/crashed window that still looks open, since I have no scripted way to
tell those apart from here; (2) that `gemini.google.com/images` still shows a
signed-in prompt box in the Aside browser's own profile. All 4 rows are still
`Failed` with `last_error` set and untouched otherwise, so re-running the
exact same command will retry them once whatever is wrong is fixed."*

## Verification (run only after a branch reports success) — SKILL.md §5

1. Every row taken in that run reads `Generated` in the manifest and its file
   exists on disk.
2. Each saved file's ratio is within 4% of its row's `aspect_ratio` (the
   script already enforces this and would have marked a mismatch `Failed`
   with `saved WxH but the row asks for ...` — so a row reading `Generated`
   has already passed this; I still spot-check by reading the manifest).
3. No two output files share a checksum:
   ```bash
   shasum -a 256 projects/<name>/images/*.png | awk '{print substr($1,1,12), $2}' | sort
   ```
4. No file is `1024px` on its long edge — the run log prints a `**` line
   naming any such row (the script's `previews` list); an absent line is the
   pass. I check the captured stdout for that line rather than re-deriving it.
5. No Gemini tab is left open in the Aside browser — the script's `finally`
   block closes every tab it opened even on failure, so this should already
   hold; I still look at the Aside window once to confirm no leftover
   `gemini.google.com` tab from an earlier cut-off run.

Only after all five hold do I report the manifest as done to the user, naming
how many rows were saved and which `--batch` value the successful run used.

## Explicit non-actions (things this plan deliberately does not do)

- Never treat "Aside is visibly open" as proof the connection is healthy —
  the whole point of this scenario is that the message is compatible with
  the app being open the entire time.
- Never restart/reinstall the Aside app as the first response to this
  message — §7 names that as the fix only for the "app is closed" half of
  the ambiguity, and explicitly rules out reinstalling for this message.
- Never lower `--batch` before at least one plain rerun has shown the failure
  recurs — §7's wording ("if it recurs with the app open") makes the rerun
  the gate before touching `--batch`, not a step to skip.
- Never invent a `--batch` value below 2 or above 4 (`MAX_BATCH = 4` in the
  script) — 3 and 2 are the only values SKILL.md names for this failure, and
  the script itself clamps `--batch` to `[1, MAX_BATCH]`.
- Never switch this manifest to a different image-generation path myself —
  that decision belongs to the caller, per the Preconditions section.
- Never edit `status`/`last_error` on the manifest by hand — the script owns
  that write-back, and doing it manually would hide whether a future rerun
  actually fixed the row.
